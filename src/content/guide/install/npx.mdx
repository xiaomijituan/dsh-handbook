## 前置：Node 与网络

```bash
node -v
npm -v
```

本页的实测环境是 Windows 11 + Node 24.18.0 + npm 11.16.0。dsh 对 Node 的最低要求以官方 README 为准，不要只照抄本页版本号。

npx 需要访问 npm registry。公司网络或代理环境下，先确认 registry 可达。

## 一行命令启动

```bash
npx @deepseek-ai/dsh@latest web
```

第一次运行会下载依赖，可能花几分钟；缓存之后启动会快很多。2026-10-27 的实测里，缓存命中后 9–14 秒就打印出了访问地址。

启动日志里会出现类似这一行：

```text
dsh web: http://127.0.0.1:3080/?token=<redacted>
```

浏览器会自动打开这个地址。加 `--no-open` 可以不自动打开：

```bash
npx @deepseek-ai/dsh@latest web --no-open
```

## latest 与 next 的区别

npm 上同时存在多个发布通道。2026-10-27 核验到的值是：

| 通道 | 版本 |
|---|---|
| latest | 0.2.1-rc.2 |
| next | 0.2.1-rc.4 |
| alpha | 0.2.1-alpha.5 |

`npx @deepseek-ai/dsh@latest web` 拿的是 latest，不是 next。想试最新的预发布版本，显式指定 `@next`：

```bash
npx @deepseek-ai/dsh@next web
```

三个通道不会自动同步，GitHub 上的最新 tag 也可能与 npm 不同。版本关系见 [版本对照](../versions.mdx)。

## 确认服务起来了

服务默认监听 `127.0.0.1:3080`。这里有一个容易误判的点：

```bash
curl -I http://127.0.0.1:3080/
```

返回 **401 Unauthorized 是正常的**。裸地址没有带上启动时生成的 token，服务会拒绝。

带 token 的地址会返回 303，并下发一个 `dsh-auth-*` cookie，然后跳回 `/`；浏览器带着这个 cookie 再请求，才拿到 200。实测结果：

| 请求 | 结果 |
|---|---|
| 不带 token 直接访问 `/` | 401 |
| 带 token 访问启动日志里的地址 | 303 → 下发 cookie |
| 跟随跳转并携带 cookie | 200 |
| 已有 cookie 再访问 `/` | 200 |

用 curl 验证时要带 cookie jar，否则会一直看到 401：

```bash
curl -L -c cookies.txt -b cookies.txt "http://127.0.0.1:3080/?token=..."
```

## 停止与升级

- 前台运行时按 `Ctrl+C`。
- 如果进程已经脱离终端，先找监听者，再按 PID 结束：

```bash
netstat -ano | grep 3080
taskkill /PID <pid> /F
```

- 升级就是重新运行 `npx @deepseek-ai/dsh@latest web`。npx 可能使用缓存，想强制拉新版本可以在命令里写明确版本号。

## 常见失败

| 报错或现象 | 原因 | 处理 |
|---|---|---|
| `EADDRINUSE: address already in use 127.0.0.1:3080` | 上一个 dsh 进程还在 | 找到占用 3080 的 PID 并结束，或换端口重启 |
| 一直 401 | 打开的是裸地址，没带 token | 用启动日志里带 `?token=` 的完整地址 |
| `ETIMEDOUT` / `ECONNRESET` | registry 或代理不可达 | 检查网络与 npm registry 配置 |
| `command not found: node` | Node 未安装或不在 PATH | 先装 Node，再重开终端 |
| 启动很慢 | 第一次下载依赖 | 等待完成；后续走缓存 |

端口占用这一条是实测中真实遇到的：上一次启动的 child 进程没有随终端退出，第二次启动直接报 `EADDRINUSE`。先清端口，再重试。
