官方文档已经把每个子系统写得很细。这个系列不复述接口表，而是按一次运行发生的顺序，把三块源码串起来：启动时插件树怎么长出来，一条消息怎么变成一个步骤，一次工具调用怎么过完关卡。

每篇的结构相同：一张图、一张源码坐标表、一段能自己跑的命令。图用来建立顺序感，坐标表用来跳进文件，命令用来确认你看到的不是文章里的二手结论。

## 三条主线

| 篇目 | 回答的问题 | 入口文件 | 你会看到 |
|---|---|---|---|
| [插件树](/source/plugin-tree/) | 一次 `dsh --profile web` 启动，96 行 base 配置怎么变成运行中的服务？ | `packages/boot/app-boot/src/profile.ts` | profile、bundle、patch、`composeEntries()`、Cordis Loader |
| [消息生命周期](/source/message-lifecycle/) | 一条 `followup()` 怎么走完 turn 和 step，什么时候写日志、什么时候发请求？ | `packages/core/agent-loop/src/agent.ts` | inbox、`agent/pre-step`、prompt 组装、请求冻结、流式结算 |
| [工具流水线](/source/tool-pipeline/) | 模型发出 `tool call` 后，谁先看一眼、谁能拒绝、失败怎么变成结果？ | `packages/core/tools/src/index.ts` | 参数快照、审批、守卫、环绕分发、`post-execute`、`finalizeContent` |

三篇有先后关系。插件树解释“东西从哪来”，消息生命周期解释“谁在驱动”，工具流水线解释“能力怎么被安全地调用”。如果只想先解决一个具体问题，也可以直接跳到对应篇目，再回头补前置概念。

## 版本先说清楚

这套文章里的行号固定在一份源码上：

- 源码标签：`dsh-v0.2.1-rc.3`
- commit：`1f81c047fc48fa190a683e469daa699857e9afe8`
- npm `latest`：`0.2.1-rc.2`
- npm `next`：`0.2.1-rc.4`

也就是说，源码读的是 rc.3，命令却在 rc.2 上实跑；`next` 线已经到 rc.4。三个通道不会自动同步，[版本页](/versions/)有完整的对照。行号只对上面这个 commit 有效，文件路径和函数名通常更耐用。

每条源码链接都指向这个 commit 的 GitHub blob，而不是 `main`。这样即使上游继续合并，你点开的仍然是文章写作时读的那份代码。

## 怎么读

1. **先看图，不看代码。** 图里的顺序就是运行时顺序；看不懂的箭头先记下来。
2. **再读“源码坐标”表。** 按行号打开文件，只读表里那几段，不要从文件第一行开始通读。
3. **最后跑“自己验证”。** 命令不需要模型 Key 的部分会标出来；需要 Key 的部分单独说明。

源码阅读最容易掉进的坑，是把“文件里存在这个函数”当成“运行时一定走这条路径”。本系列每篇都尽量追到实际调用点：谁调用、在什么条件下调用、失败时走哪条分支。如果某个结论只来自注释或类型声明，文中会直接说“这是注释里的约束”，不会把它写成实测行为。

## 实验环境

- Windows 11（10.0.26200），Node 24.18.0，npm 11.16.0
- `dsh` 0.2.1-rc.2，通过 `npx -y @deepseek-ai/dsh@0.2.1-rc.2` 运行
- 源码：`dsh-v0.2.1-rc.3` 的 codeload 压缩包，解压后按 tag 对应的 commit 核对
- 需要 pnpm 的命令单独标注；`dsh plugin` 会把参数转发给 profile 目录里的 pnpm

不需要模型 Key 的实验包括 `--dump-config`、源码 grep 和插件加载日志。需要 Key 的实验会明确写出，不把“没跑过”说成“跑过了”。
